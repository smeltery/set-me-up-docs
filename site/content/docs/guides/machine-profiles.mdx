<span id="two-kinds" />

## Two kinds of profile

A built-in machine profile is a preset defined by smu. It describes a machine role, default modules and adapter, submodule scope, and safety defaults. A blueprint profile is a named table in your own smu.toml. It lets you version module selections and adapter overrides alongside your dotfiles.

| Task | Command |
| --- | --- |
| Inspect a built-in role | smu machine-profile show vps --json |
| Plan using a built-in role | smu plan --machine vps --json |
| Preflight a named blueprint profile | smu provisioning-adapter preflight --profile lab --json |

<span id="inspect" />

## Inspect the available presets

Use the list command to get the IDs shipped with your installed version. The show command includes the proposed module list and safety settings. Pick the role closest to the host and confirm its modules are available in your blueprint. The built-in vps, ci, and agent-host setup paths require Debian-based systems.

```bash title="Terminal"
smu machine-profile list --json
smu machine-profile show vps --json
```

<span id="plan-role" />

## Preview a built-in role on the host

Run the plan on the machine you intend to configure. A machine preset supplies an adapter default to the plan, and the --provisioning-adapter option lets you compare another choice. For example, inspect the same Debian VPS modules with the rcm adapter used by a traditional blueprint.

In the result, review provisioning.modules and provisioning.adapter, then look at dotfile conflicts, secret findings, trust warnings, and rollback coverage. Treat the plan as a review artifact before running the actual setup.

```bash title="Terminal"
smu plan --machine vps --provisioning-adapter rcm --json
```

<span id="compose" />

## Keep a custom profile in the blueprint

Add a profile for a repeatable combination of modules. This example keeps the stock blueprint’s example module in the default profile and creates a lab profile with the same module. Once it works, add modules that your own lab needs.

Choose the module names from smu --list-modules on the target host. A profile can override the global adapter, so keep its module set compatible with that adapter.

```toml title="smu.toml"
[provisioning]
adapter = "rcm"

[profile.default]
modules = ["example"]

[profile.lab]
adapter = "rcm"
modules = ["example"]
```

<span id="preflight" />

## Validate the custom profile

Preflight with the same profile name you will use when applying the adapter. Check the module coverage and the proposed command. An unknown built-in role from smu machine-profile show indicates that you passed an ID outside the built-in list. Use the adapter preflight’s --profile argument for names declared in smu.toml.

```bash title="Terminal"
smu provisioning-adapter preflight --adapter rcm --profile lab --json
```

<span id="design-profiles" />

## Design profiles around machine responsibilities

A profile should explain why a group of modules belongs together. A workstation may need interactive tools and application preferences; a headless server should avoid desktop assumptions. Reusing a module across both roles is appropriate only when its implementation supports both environments.

Prefer a small shared baseline and explicit role-specific additions. Keep the profile in the blueprint so reviewers can see how a module-selection change affects each machine. Names such as lab are examples from your configuration, not built-in smu machine IDs.

## Review a profile again on a different host

A configuration that works on one computer is evidence about that computer. Operating-system packages, architecture, permissions, and existing files can differ on the next host. Run discovery and preflight there instead of assuming that a shared profile makes the environment identical.

If a module is unavailable, confirm its checkout and supported host bucket before substituting another one. Record intentional platform differences in configuration rather than making unexplained local edits.
