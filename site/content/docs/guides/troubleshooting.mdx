<span id="orient" />

## Confirm the shell and blueprint

Start in the terminal where the problem appears. Use command -v to see which smu the shell runs. An empty result means the command is unavailable on that shell’s PATH. Check that bootstrap completed and restart the shell before changing machine settings.

Check SMU_HOME_DIR next. With no override, smu uses the set-me-up directory under your home directory. In a multi-checkout workflow, identify the active blueprint before you inspect files or retry a change.

```bash title="Terminal"
command -v smu
blueprint_dir="${SMU_HOME_DIR:-$HOME/set-me-up}"
printf "%s\n" "$blueprint_dir"
git -C "$blueprint_dir" status --short
```

<span id="health" />

## Collect read-only diagnostics

The general doctor reports installer health, profile and adapter checks, conflicts, and update readiness. Use status to see module detection and update doctor for a problem specific to Git or submodule updates.

Read the first failed check and its path before fixing anything. Status can infer whether a declarative package or an entry is present, but a shell module’s effects may require checking the resulting application or configuration directly.

```bash title="Terminal"
smu doctor --json
smu status --json
smu update doctor --json
```

<span id="symptoms" />

## Match the symptom to the next check

Use these checks to narrow the issue. Fix one cause at a time, then run the same check again so you can tell whether the repair worked.

| Symptom | Next step |
| --- | --- |
| Module is missing from the list | Check the module name and host bucket. Use smu --list-modules --all to see whether it exists for a different platform. |
| Dotfile points at an unexpected source | Run smu --lsrc and inspect the tag order and active blueprint. |
| Preflight reports an unavailable adapter | Check supported hosts, required tools, and module adapter coverage. |
| Update reports a dirty checkout | Use Git status to find the local change. Commit or stash work you want to keep before retrying. |
| Theme appears unchanged in a new terminal | Run smu profile and inspect environment and machine-local overrides. |

<span id="recovery" />

## Preview the recovery

If the original operation recorded a state event, the rollback doctor explains whether the event has automatic, partial, or manual recovery coverage. The dry run lets you see the proposed inverse steps before changing the host.

Keep a copy of the current file or checkout before applying recovery. Use the run’s status and the affected application as your final checks. For script modules with manual recovery, inspect the module’s writes and restore only the paths it owns.

```bash title="Terminal"
smu rollback doctor --json
smu rollback --dry-run
```

<span id="report" />

## Collect a report you can share

A support bundle records versions, health checks, module status, and plan details. The redaction step masks recognized secret patterns. Read the resulting file before attaching it to an issue, and remove remaining private hostnames, repository names, paths, or any sensitive values.

Include what you expected to happen, the exact command you ran, the first failed check, and what changed since the last successful run. A short reproducible sequence helps someone identify the failing layer.

```bash title="Terminal"
smu support bundle --redact --output support.json
```

<span id="failure-layers" />

## Find the failing layer before retrying

Start with the earliest relevant error, rather than the last line printed by a wrapper. Separate source retrieval, blueprint validation, module discovery, adapter coverage, execution, and application behavior. Each layer has different evidence and a different repair.

A missing module can mean the checkout scope excluded its source. An unsupported adapter can mean the module exists but has no implementation for that adapter. A successful module can still need application-specific verification. These are different failures and should not all be handled by reinstalling the blueprint.

<span id="good-reproduction" />

## Write a useful reproduction

Describe the host platform, blueprint revision, selected profile or module, exact command, and first error. Explain what you expected and how you verified the actual result. Include whether this was a new machine, an update, or a retry after a partial run.

Use a minimal module selection when reproducing the failure. Remove credentials from reports and check command output for private repository URLs or hostnames. A small reproducible case is easier to test than a complete dump of a personal setup.
